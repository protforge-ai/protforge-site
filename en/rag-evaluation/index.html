What goes wrong in RAG systems and agents

A RAG answer can be wrong for several unrelated reasons, and each one has a different fix. Measuring them separately is most of the work.

Retrieval recall and precision

Does the retriever return the passage that contains the answer, and how much irrelevant text comes with it? We measure this on a gold set of questions with the correct source passages marked. Many answers that look like model hallucinations are retrieval misses.

Groundedness and faithfulness

Is every claim in the answer supported by the retrieved context? An answer can be correct in the real world and still ungrounded, which matters if your users rely on your documents as the source of truth.

Citation correctness

When the answer cites a source, does that source actually say what is claimed? Citations that point to the wrong passage look reassuring and are worse than none.

Completeness and refusal behaviour

Does the answer cover everything the question needs, and does the system say it does not know when the documents do not contain the answer? Both over-answering and over-refusing are failures.

Tool-call errors and multi-step failures

For agents: wrong tool, wrong or missing arguments, loops, skipped steps, no recovery after a tool error, and final answers that ignore what a tool returned.

Regression suite in CI

The golden set and checks run on every prompt, model or retrieval change, so a fix in one place does not quietly break another.

How to evaluate your RAG in 5 steps

This works with or without us. Do it by hand first; automate once you trust the labels.

Build a gold set from real questions

Pull 50 to 100 questions from logs, support tickets or search queries rather than inventing them. For each one, have a person write the expected answer and mark the passage that supports it. Include questions the documents cannot answer, so you can test refusals.

Evaluate retrieval on its own

Before looking at any generated text, check recall at k (is the right passage in the top k results?) and precision. If recall is low, no prompt change will fix the answers. Chunking, embeddings, filters and query rewriting come first.

Score the generated answers

Check groundedness against the retrieved context, correctness against the gold answer, citation accuracy and completeness. Count failures per category instead of using one overall score, so you know what to fix.

Calibrate any LLM judge against human labels

Off-the-shelf LLM-as-judge prompts disagree with people more often than teams expect, and they drift when you change the judge model. Have humans label a sample, compute agreement per criterion, and use the judge only where it agrees. Re-check when the judge model changes.

Turn failures into a regression suite

Every failure you find becomes a test case. Run the suite in CI on each change and track the rates over time, plus latency and cost per answer, so you see what an improvement costs.

For checking groundedness automatically we use our open-source package groundcheck, and we publish a comparison of hallucination detectors so you can see how the detectors themselves perform before you rely on one.

How many labelled examples do I need to evaluate a RAG system?

Start with 50 to 100 real questions with the expected answer and the source passage marked by a person. That is enough to see the big failure modes and to compare two configurations roughly. Grow it to a few hundred as you find new failure types, and always add the failures you see in production.

Can I just use an LLM as a judge?

You can, but not without checking it. An LLM judge has its own biases, such as favouring longer answers, and its scores shift with the judge model and the prompt. Label a sample by hand, measure how often the judge agrees with the humans, and only trust the judge on the criteria where agreement is high. We do this calibration as part of the audit.

How do you evaluate AI agents, not just RAG?

We look at the whole run, not only the final answer: whether the right tool was called with the right arguments, whether the agent loops or skips steps, whether it recovers from tool errors and whether the final answer matches what the tools returned. Each of these becomes a test case in a regression suite.
